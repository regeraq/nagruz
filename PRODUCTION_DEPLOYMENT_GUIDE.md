# 🚀 Полное руководство по публикации сайта в интернете

Документ ведёт от нулевого состояния (нет ни домена, ни сервера) до
работающего сайта на HTTPS с автозапуском, бэкапами и мониторингом.

**Кому адресовано:** разработчику или администратору, который впервые
разворачивает этот проект. Предполагается базовое умение работать в терминале
Linux; всё остальное объясняется по шагам.

**Сколько времени займёт:** 2–4 часа в первый раз, из них ~30 минут ожидания
(регистрация домена, обновление DNS).

## 1. Что мы разворачиваем

Приложение — единый Node.js-процесс, который одновременно отдаёт собранный
React-фронтенд и обслуживает REST API. Данные лежат в PostgreSQL.
Снаружи стоит nginx: он терминирует HTTPS и проксирует запросы в Node.

```
Интернет → nginx (443, HTTPS) → Node.js (127.0.0.1:5000) → PostgreSQL (5432)
                                       ↑
                                   PM2 (автозапуск, перезапуск при сбое)
```

Отдельного веб-сервера для статики не нужно, Docker не используется.

**Технологии:** Node.js 20+, PostgreSQL 14+, nginx, PM2, Let's Encrypt.

## 2. Выбор и покупка домена

### 2.1. Где покупать

Проект обрабатывает персональные данные граждан РФ, поэтому и регистратор,
и хостинг желательно брать российские — так проще выполнять требования
152-ФЗ и 242-ФЗ (локализация данных).

| Регистратор | Цена `.ru` в год | Комментарий |
|---|---|---|
| **REG.RU** | ~250–900 ₽ | Крупнейший в РФ, простая панель. Хороший выбор по умолчанию |
| **Timeweb** | ~250–900 ₽ | Удобно, если сервер тоже берёте у Timeweb |
| **Beget** | ~250–900 ₽ | Приятная панель, бесплатный DNS |
| **RU-CENTER (nic.ru)** | ~1000+ ₽ | Старейший, дороже, но очень надёжен |

Цены на первый год часто акционные (от 99 ₽); смотрите **стоимость продления** —
именно её вы будете платить каждый год.

### 2.2. Какую зону выбрать

- **`.ru`** — оптимально для бизнеса в России. Дёшево, привычно, хорошо
  воспринимается поисковиками при продвижении по РФ.
- **`.рф`** — можно взять дополнительно и настроить редирект на основной домен.
- **`.com`** — если планируется выход за пределы РФ.

Не берите экзотические зоны (`.site`, `.online`, `.xyz`) для коммерческого
проекта: они дороже при продлении и хуже воспринимаются как надёжные.

### 2.3. Обязательные настройки при покупке

1. **Включите автопродление.** Самая частая причина падения сайтов —
   забытое продление домена. После истечения домен уходит в
   карантин на 30 дней, а затем может быть куплен кем угодно.
2. **Укажите настоящий e-mail** и проверьте, что письма от регистратора
   доходят: на этот адрес придёт подтверждение и напоминания о продлении.
3. **Подтвердите e-mail в течение 15 дней.** Иначе ICANN/координатор может
   приостановить делегирование домена.
4. **Включите защиту от передачи** (Transfer Lock), если регистратор
   предлагает — защита от угона домена.
5. **Скройте персональные данные в WHOIS** (обычно бесплатно для физлиц) —
   меньше спама и меньше рисков социальной инженерии.

## 3. Выбор и покупка сервера

### 3.1. Требования приложения

Реальное потребление одного процесса Node.js в этом проекте — **150–400 МБ RAM**
(в PM2 стоит перезапуск при превышении 500 МБ). PostgreSQL в базовой
конфигурации просит ещё ~150–250 МБ. Плюс сама ОС ~200–300 МБ.

Отсюда абсолютный минимум — 2 ГБ RAM. На 1 ГБ сборка фронтенда (`npm run build`,
Vite) почти наверняка упадёт с `JavaScript heap out of memory`.

### 3.2. Три конфигурации

#### 🟢 Минимальный бюджет — «сайт с небольшим трафиком»

Подходит для запуска, до ~5 000 посетителей в месяц.

| Параметр | Значение |
|---|---|
| **RAM** | 2 ГБ |
| **CPU** | 1 vCPU |
| **SSD (NVMe)** | 20–30 ГБ |
| **Трафик** | от 1 ТБ/мес |
| **ОС** | Ubuntu 24.04 LTS |
| **Цена** | 300–600 ₽/мес |
| **Провайдеры** | Timeweb Cloud, Beget, RU VDS, Aeza |

Резерв по нагрузке: **выдержит ~30–50 одновременных посетителей.**
БД и приложение живут на одной машине. Сборка проекта пройдёт, но медленно
(2–4 минуты) — обязательно настройте swap (см. §6.6), иначе есть риск OOM.

#### 🔵 Средний бюджет — **рекомендуется для production**

Оптимальный баланс. До ~50 000 посетителей в месяц.

| Параметр | Значение |
|---|---|
| **RAM** | 4 ГБ |
| **CPU** | 2 vCPU |
| **SSD (NVMe)** | 50–80 ГБ |
| **Трафик** | от 2 ТБ/мес |
| **ОС** | Ubuntu 24.04 LTS |
| **Цена** | 700–1500 ₽/мес |
| **Провайдеры** | Timeweb Cloud, Selectel, VK Cloud, Yandex Cloud |

Резерв по нагрузке: **~150–300 одновременных посетителей**, двукратный запас
по памяти на пики и на сборку без риска OOM. Это та конфигурация, с которой
стоит выходить в интернет.

#### 🟣 Для роста — «нагрузка растёт, нужен запас»

От ~100 000 посетителей в месяц или когда появляются жалобы на скорость.

| Параметр | Значение |
|---|---|
| **RAM** | 8 ГБ и больше |
| **CPU** | 4 vCPU |
| **SSD (NVMe)** | 100–160 ГБ |
| **Трафик** | от 4 ТБ/мес |
| **ОС** | Ubuntu 24.04 LTS |
| **Цена** | 2000–4000 ₽/мес |
| **Провайдеры** | Selectel, VK Cloud, Yandex Cloud (управляемый PostgreSQL) |

На этом этапе имеет смысл:
- **Вынести PostgreSQL на отдельный сервер** или взять управляемую БД
  (Yandex Managed PostgreSQL, Selectel DBaaS) — бэкапы и репликация из коробки.
- **Перевести PM2 в cluster mode** (`instances: 'max'`, `exec_mode: 'cluster'`
  в `ecosystem.config.cjs`) — использует все ядра и даёт реальный
  zero-downtime reload.
- **Подключить CDN** для статики.
- **Заменить in-memory кэш на Redis** (в `server/cache.ts` есть задел).

### 3.3. Важно при выборе провайдера

- **Локация — Россия (Москва/СПб).** Это требование 242-ФЗ: базы с
  персональными данными граждан РФ должны находиться на территории РФ.
  Не берите серверы в Европе или США.
- **NVMe, а не HDD.** На HDD сборка и запросы к БД будут заметно медленнее.
- **Резервные копии на стороне провайдера.** Многие дают снапшоты за
  небольшую доплату — берите, это независимый уровень защиты в дополнение
  к нашим бэкапам.
- **Ubuntu 24.04 LTS** (поддержка до 2029). Можно 22.04 LTS. Не берите
  Debian, CentOS или не-LTS версии Ubuntu — инструкции ниже рассчитаны
  на Ubuntu LTS, а на других системах имена пакетов отличаются.

## 4. Настройка DNS

DNS связывает домен с IP-адресом сервера. Нужен уже купленный сервер — его
IP вы увидите в панели провайдера (например, `203.0.113.10`).

### 4.1. Добавьте две A-записи

В панели регистратора откройте «DNS-записи» / «Управление зоной» и создайте:

| Тип | Имя (Host) | Значение | TTL |
|---|---|---|---|
| `A` | `@` | `203.0.113.10` | 3600 |
| `A` | `www` | `203.0.113.10` | 3600 |

`@` означает сам домен (`example.ru`), `www` — поддомен `www.example.ru`.
Вместо `203.0.113.10` подставьте IP своего сервера.

> Некоторые панели вместо `@` требуют оставить поле пустым или ввести
> сам домен целиком. Смотрите подсказки конкретного регистратора.

### 4.2. Дождитесь распространения

Обновление занимает от 10 минут до 24 часов (обычно ~30 минут). Проверка:

```bash
# С сервера или локально:
dig +short example.ru
nslookup example.ru
```

Команда должна вернуть IP вашего сервера. **Не переходите к получению
SSL-сертификата, пока она не вернёт правильный IP** — Let's Encrypt проверяет
домен через DNS и выдаст ошибку.

### 4.3. DNS-записи для почты

Если вы отправляете письма (а проект отправляет — подтверждение e-mail,
уведомления о заявках), нужны записи SPF/DKIM/DMARC, иначе письма будут
попадать в спам. Конкретные значения выдаёт почтовый провайдер —
см. §10.1.

## 5. Первое подключение и защита сервера

### 5.1. Подключитесь по SSH

```bash
# Windows (PowerShell), macOS, Linux — команда одинаковая:
ssh root@203.0.113.10
```

Пароль root пришёл в письме от провайдера. При первом подключении
согласитесь с отпечатком ключа (`yes`).

### 5.2. Обновите систему

```bash
apt update && apt upgrade -y
```

### 5.3. Создайте отдельного пользователя

Работать под root постоянно — плохая практика: любая ошибка или
скомпрометированный процесс получает полный контроль над машиной.

```bash
adduser deploy                  # задайте стойкий пароль
usermod -aG sudo deploy
```

### 5.4. Настройте вход по SSH-ключу

Пароли можно подобрать, ключи — нет. **Со своей локальной машины:**

```bash
# Создать ключ (если ещё нет). Enter на все вопросы, но задайте passphrase:
ssh-keygen -t ed25519 -C "deploy@loaddevice"

# Скопировать публичный ключ на сервер:
ssh-copy-id deploy@203.0.113.10
```

Если `ssh-copy-id` недоступен (типично для Windows):

```powershell
# Windows PowerShell:
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh deploy@203.0.113.10 "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

**Проверьте, что вход по ключу работает,** прежде чем отключать пароли:

```bash
ssh deploy@203.0.113.10    # должно войти без запроса пароля
```

### 5.5. Отключите вход по паролю и под root

Только после успешной проверки из предыдущего пункта!

```bash
sudo nano /etc/ssh/sshd_config
```

Найдите и приведите к такому виду:

```
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
```

```bash
sudo systemctl restart ssh
```

> ⚠️ **Не закрывайте текущую SSH-сессию**, пока не убедились в новом окне,
> что вход по ключу всё ещё работает. Иначе можно потерять доступ к серверу
> и придётся заходить через VNC-консоль провайдера.

### 5.6. Настройте фаервол

Наружу должны смотреть только SSH, HTTP и HTTPS. Порт приложения (5000) и
PostgreSQL (5432) обязаны быть доступны **только локально**.

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable          # подтвердите: y
sudo ufw status verbose
```

Порты 5000 и 5432 не открываем — nginx обращается к приложению через
`127.0.0.1`, наружу они не нужны.

### 5.7. Защита от перебора SSH

```bash
sudo apt install -y fail2ban
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd
```

Fail2ban автоматически блокирует IP после нескольких неудачных попыток входа.

### 6.6. Swap (обязательно при 2 ГБ RAM)

Swap спасает от падения сборки по нехватке памяти. На 2 ГБ RAM —
обязателен, на 4 ГБ — желателен.

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

# Реже уходить в swap, пока есть свободная RAM:
echo 'vm.swappiness=10' | sudo tee -a /etc/sysctl.conf
sudo sysctl -p

free -h    # проверка: в строке Swap должно быть 2Gi
```

## 7. Настройка PostgreSQL

### 7.1. Создайте базу и пользователя

Сгенерируйте стойкий пароль и **сразу сохраните его** — он понадобится
в `.env`:

```bash
openssl rand -base64 24
```

```bash
sudo -u postgres psql
```

В консоли psql (подставьте свой пароль вместо `ВАШ_ПАРОЛЬ`):

```sql
CREATE DATABASE loaddevice_db;
CREATE USER loaddevice_user WITH ENCRYPTED PASSWORD 'ВАШ_ПАРОЛЬ';
GRANT ALL PRIVILEGES ON DATABASE loaddevice_db TO loaddevice_user;

-- Права на схему public (обязательно для PostgreSQL 15+,
-- иначе приложение не сможет создавать таблицы):
\c loaddevice_db
GRANT ALL ON SCHEMA public TO loaddevice_user;
ALTER SCHEMA public OWNER TO loaddevice_user;

\q
```

### 7.2. Проверьте подключение

```bash
psql "postgresql://loaddevice_user:ВАШ_ПАРОЛЬ@localhost:5432/loaddevice_db" -c "SELECT version();"
```

Если вывелась версия PostgreSQL — всё в порядке.

### 7.3. Убедитесь, что БД не смотрит в интернет

```bash
sudo grep -E "^listen_addresses" /etc/postgresql/*/main/postgresql.conf
```

Должно быть `localhost` или строка закомментирована (по умолчанию это так).
Если стоит `*` — измените на `localhost` и перезапустите:
`sudo systemctl restart postgresql`.

## 9. Настройка переменных окружения

Это самый ответственный шаг. Ошибки здесь — причина большинства проблем
при первом запуске. Приложение проверяет конфигурацию при старте
(preflight) и откажется запускаться при критических ошибках.

### 9.1. Сгенерируйте секреты

Нужны **три разных** значения. Выполните команду трижды и сохраните
результаты:

```bash
openssl rand -base64 48
```

> ⚠️ Секреты обязаны быть разными. Если `JWT_SECRET` совпадёт с
> `JWT_REFRESH_SECRET`, короткоживущий access-токен станет приниматься
> как refresh-токен, и время жизни сессии вырастет с 1 дня до 7. Приложение
> проверяет это при старте и не запустится.

### 9.2. Создайте `.env`

```bash
cd /var/www/loaddevice
cp .env.example .env
nano .env
```

Заполните так (подставьте свои значения):

```ini
# ---------- База данных ----------
DATABASE_URL=postgresql://loaddevice_user:ВАШ_ПАРОЛЬ_БД@localhost:5432/loaddevice_db

# ---------- Окружение ----------
NODE_ENV=production
PORT=5000

# ОБЯЗАТЕЛЬНО true — приложение работает за nginx.
# При false все посетители выглядят как 127.0.0.1, и защита от перебора
# паролей начинает блокировать вход сразу всем сразу.
TRUST_PROXY=true

# ОБЯЗАТЕЛЬНО true — TLS терминируется на nginx, сам Node видит HTTP
# и без этого флага не поставит на cookie флаг Secure.
FORCE_SECURE_COOKIES=true

# ---------- CORS ----------
# Оставьте ПУСТЫМ, если фронтенд и API на одном домене (наш случай).
ALLOWED_ORIGINS=

# ---------- Секреты (три РАЗНЫХ значения!) ----------
```

## 10. Внешние сервисы: почта и остальное

### 10.1. Почта — Yandex Cloud Postbox (ОБЯЗАТЕЛЬНО)

Без настроенной почты не работают подтверждение e-mail при регистрации,
восстановление доступа и уведомления о новых заявках.

Выбран Yandex Cloud Postbox: серверы в РФ, что снимает вопрос
трансграничной передачи персональных данных по 152-ФЗ.

**Шаги:**

1. Зарегистрируйтесь на [console.yandex.cloud](https://console.yandex.cloud),
   создайте платёжный аккаунт (есть пробный грант).
2. Создайте каталог, подключите сервис **Postbox**.
3. **Адресные идентичности → Создать** → укажите домен `example.ru`.
4. Postbox выдаст DNS-записи для подтверждения домена (DKIM — обычно три
   CNAME-записи, а также SPF и DMARC). Добавьте их **все** в DNS у
   регистратора, как в §4.1.
5. Дождитесь статуса «Подтверждён» (от 15 минут до нескольких часов).
6. **Сервисные аккаунты** → создайте аккаунт → роль `postbox.sender`.
7. У сервисного аккаунта: **API-ключи → Создать статический ключ доступа**.
   Скопируйте **Key ID** и **Secret** — секрет показывается один раз.
8. Впишите их в `.env` как `YANDEX_POSTBOX_KEY_ID` и `YANDEX_POSTBOX_SECRET`.

**Обязательные DNS-записи для почты.** Без них письма уходят в спам:

| Тип | Назначение | Значение |
|---|---|---|
| `TXT` (SPF) | кто вправе отправлять от вашего домена | выдаёт Postbox |
| `CNAME` ×3 (DKIM) | подпись писем | выдаёт Postbox |
| `TXT` (DMARC) | политика при непрохождении проверок | `v=DMARC1; p=none; rua=mailto:admin@example.ru` |

Начните с DMARC `p=none` (только наблюдение). Через 2–4 недели, убедившись
по отчётам, что легитимные письма проходят, переходите на `p=quarantine`.

**Проверка после настройки:** войдите в админку → раздел настроек почты →
«Отправить тестовое письмо». Или из терминала посмотрите логи:
`pm2 logs loaddevice | grep email`.

### 10.2. Полный перечень внешних сервисов

| Сервис | Статус | Что даёт | Рекомендация |
|---|---|---|---|
| **SMTP / транзакционные письма** | 🔴 **Обязательно** | Регистрация, восстановление пароля, уведомления о заявках | Yandex Cloud Postbox (§10.1) |
| **Резервное копирование** | 🔴 **Обязательно** | Защита от потери данных | `scripts/backup.sh` + cron (§15) |
| **Копии вне сервера** | 🔴 **Обязательно** | Бэкап на том же диске бесполезен при отказе сервера | Yandex Object Storage / снапшоты провайдера (§15.4) |
| **SSL-сертификат** | 🔴 **Обязательно** | HTTPS | Let's Encrypt, бесплатно (§13) |
| **Мониторинг доступности** | 🟡 Желательно | Узнать о падении раньше клиентов | UptimeRobot (бесплатно, §16.3) |
| **Мониторинг ошибок** | 🟡 Желательно | Видеть исключения с трассировкой | Sentry / GlitchTip (§16.4) |
| **Ротация логов** | 🟡 Желательно | Логи не съедят диск | `pm2-logrotate` (§16.2) |
| **Уведомления администратора** | 🟡 Желательно | Оперативная реакция на сбои | Telegram-бот (§16.5) |
| **Аналитика** | 🟡 Желательно | Понимать поведение посетителей | Яндекс Метрика (РФ, 152-ФЗ) |
| **CAPTCHA / антиспам** | 🟡 Желательно | Защита форм от ботов | Yandex SmartCaptcha |
| **Файловое хранилище (S3)** | ⚪ Необязательно | Сейчас файлы лежат в БД — работает, но раздувает бэкапы | Yandex Object Storage при росте |
| **CDN** | ⚪ Необязательно | Ускорение статики для удалённых регионов | Yandex Cloud CDN при росте |
| **Почтовые рассылки** | ⚪ Необязательно | Маркетинг. В проекте не используется | Unisender / Sendsay, нужно отдельное согласие по 152-ФЗ |
| **Redis** | ⚪ Необязательно | Кэш и rate limiting между процессами | Только в cluster mode / на нескольких серверах |

**Что уже встроено в проект и не требует внешних сервисов:**
ограничение частоты запросов, защита от перебора паролей, CSRF-защита,
security-заголовки и CSP, журнал действий администраторов, health check,
автоматическая очистка устаревших данных.

**О CAPTCHA.** Формы уже защищены rate limiting, а форма коммерческого
предложения требует авторизации, поэтому CAPTCHA не блокер. Подключайте,
если начнёт приходить спам.

**Об аналитике и 152-ФЗ.** При подключении Метрики появляется передача
данных третьему лицу — это нужно отразить в политике конфиденциальности,
а баннер cookie-согласия должен ставить скрипт только после согласия.

## 12. Настройка nginx

Готовый конфиг лежит в репозитории — не пишите его с нуля.

```bash
cd /var/www/loaddevice
sudo cp deploy/nginx.conf /etc/nginx/sites-available/loaddevice

# Подставьте свой домен вместо example.ru:
sudo sed -i 's/example\.ru/ВАШ_ДОМЕН.ru/g' /etc/nginx/sites-available/loaddevice

sudo ln -sf /etc/nginx/sites-available/loaddevice /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default    # убираем страницу-заглушку
```

### 12.1. Временно отключите редирект на HTTPS

Сертификата ещё нет, поэтому сайт должен работать по HTTP — иначе
certbot не сможет пройти проверку.

```bash
sudo nano /etc/nginx/sites-available/loaddevice
```

В блоке `server` для порта 80:
- закомментируйте строку `return 301 https://$host$request_uri;`
- раскомментируйте блок `location /` с `proxy_pass` (он идёт следом
  и уже подготовлен, нужно снять `#`).

Дополнительно закомментируйте **весь блок `server` для порта 443** — он
ссылается на несуществующие файлы сертификатов и на
`/etc/letsencrypt/options-ssl-nginx.conf`, который появится только после
запуска certbot. Без этого nginx не запустится.

**Про HTTP/2.** Проверьте версию nginx:

```bash
nginx -v
```

- **1.25.1 и новее** — раскомментируйте в блоке 443 строку `http2 on;`.
- **1.24 и старее** (в Ubuntu 24.04 из репозитория идёт 1.24) — вместо
  этого допишите `http2` в директивы `listen`:
  `listen 443 ssl http2;`.

В конфиге оба варианта описаны в комментариях; по умолчанию HTTP/2
выключен, чтобы nginx точно запустился на любой версии.

Создайте директорию для проверки Let's Encrypt:

```bash
sudo mkdir -p /var/www/certbot
```

### 12.2. Проверьте и примените

```bash
sudo nginx -t                     # обязательно: "syntax is ok / test is successful"
sudo systemctl reload nginx
```

Запустите приложение (`node dist/index.js` в отдельном окне) и откройте
`http://ВАШ_ДОМЕН.ru` — сайт должен открыться по HTTP.

## 13. Получение SSL-сертификата

HTTPS обязателен: без него пароли и персональные данные передаются
открытым текстом, а браузеры помечают сайт как небезопасный.
Let's Encrypt бесплатен, сертификат выдаётся на 90 дней и продлевается
автоматически.

### 13.1. Установите certbot

```bash
sudo apt install -y certbot python3-certbot-nginx
```

### 13.2. Получите сертификат

**Проверьте перед запуском:** `dig +short ВАШ_ДОМЕН.ru` возвращает IP
сервера, и сайт открывается по HTTP. Иначе выпуск завершится ошибкой.

```bash
sudo certbot --nginx -d ВАШ_ДОМЕН.ru -d www.ВАШ_ДОМЕН.ru
```

Certbot спросит:
- **e-mail** — укажите настоящий, на него придут предупреждения об
  истечении сертификата;
- **согласие с условиями** — `A`;
- **рассылку** — `N`;
- **редирект HTTP → HTTPS** — выберите **`2` (Redirect)**.

Certbot сам впишет пути к сертификатам в конфиг nginx и перезагрузит его.

> Если вы закомментировали блок 443 в §12.1, раскомментируйте его перед
> запуском certbot либо позвольте certbot создать конфигурацию сам.

### 13.3. Проверьте автопродление

```bash
sudo certbot renew --dry-run
sudo systemctl status certbot.timer     # должен быть active
```

Systemd-таймер запускает продление дважды в сутки; сертификат обновляется
за 30 дней до истечения. Ручных действий не требуется.

### 13.4. Включите HSTS

В `deploy/nginx.conf` заголовок `Strict-Transport-Security` уже прописан.
Убедитесь, что HTTPS стабильно работает **несколько дней**, и только потом
оставляйте его включённым: браузеры запоминают эту политику на год и
откажутся открывать сайт по HTTP, если что-то сломается.

### 13.5. Проверьте качество настройки TLS

Откройте [ssllabs.com/ssltest](https://www.ssllabs.com/ssltest/) и введите
свой домен. С конфигом из репозитория ожидается оценка **A** или **A+**.

## 14. Автозапуск через PM2

Без этого шага приложение не поднимется после перезагрузки сервера.

### 14.1. Запустите под PM2

```bash
cd /var/www/loaddevice
mkdir -p logs
pm2 start ecosystem.config.cjs
pm2 status        # status должен быть online
pm2 logs loaddevice --lines 30
```

### 14.2. Включите автозапуск при загрузке ОС

```bash
pm2 startup
# Команда напечатает строку, начинающуюся с "sudo env PATH=...".
# Скопируйте её целиком и выполните.

pm2 save          # запоминает текущий список процессов
```

### 14.3. Проверьте, что автозапуск работает

Единственная надёжная проверка — перезагрузка:

```bash
sudo reboot
```

Подождите минуту, подключитесь снова и убедитесь:

```bash
pm2 status                                   # loaddevice — online
curl -s http://127.0.0.1:5000/api/health     # {"status":"ok",...}
```

### 14.4. Закройте служебные файлы PM2

`ecosystem.config.cjs` передаёт переменные из `.env` в окружение процесса,
а `pm2 save` записывает их в `~/.pm2/dump.pm2` — в открытом виде. Файл
нужно закрыть от других пользователей системы так же, как сам `.env`:

```bash
chmod 700 ~/.pm2
chmod 600 ~/.pm2/dump.pm2
ls -ld ~/.pm2 && ls -l ~/.pm2/dump.pm2
```

Повторяйте после каждого `pm2 save` (или просто проверяйте при обновлениях).

### 14.5. Полезные команды PM2

```bash
pm2 status                    # состояние процессов
pm2 logs loaddevice           # логи в реальном времени
pm2 logs loaddevice --err     # только ошибки
pm2 reload ecosystem.config.cjs --update-env   # перезапуск с новым .env
pm2 restart loaddevice        # жёсткий перезапуск
pm2 stop loaddevice           # остановить
pm2 monit                     # интерактивный монитор CPU/RAM
```

> Используйте `reload`, а не `restart`: приложение обрабатывает SIGTERM и
> корректно завершает запросы, которые уже выполняются, вместо того чтобы
> обрывать их на полуслове.
>
> После изменения `.env` обязателен флаг `--update-env` — иначе PM2
> запустит процесс со старыми переменными.

## 15. Резервное копирование

**Без бэкапов проект нельзя считать готовым к production.** Отказ диска,
ошибочный `DELETE` или неудачная миграция без резервной копии означают
безвозвратную потерю всех данных.

### 15.1. Что сохраняется

Скрипт `scripts/backup.sh` создаёт:
- **дамп PostgreSQL** (`pg_dump`, custom format) — все данные;
- **архив файлов** — `.env`, папку `uploads`, конфиг nginx.

Копии складываются в `/var/backups/loaddevice`, хранятся 14 дней,
но не менее 7 последних штук каждого типа.

### 15.2. Проверьте вручную

```bash
cd /var/www/loaddevice
bash scripts/backup.sh
ls -lh /var/backups/loaddevice
```

Должны появиться `loaddevice-db-*.dump` и `loaddevice-files-*.tar.gz`
ненулевого размера.

### 15.3. Настройте ежедневный запуск

```bash
crontab -e
```

Добавьте строку (запуск в 03:30 каждый день):

```cron
30 3 * * * /bin/bash /var/www/loaddevice/scripts/backup.sh >> /var/log/loaddevice-backup.log 2>&1
```

Проверьте: `crontab -l`.

Настройки при необходимости меняются в `/etc/loaddevice-backup.env`:

```bash
sudo tee /etc/loaddevice-backup.env <<'EOF'
PROJECT_DIR=/var/www/loaddevice
BACKUP_DIR=/var/backups/loaddevice
KEEP_DAYS=14
KEEP_MIN=7
EOF
```

### 15.4. Копии вне сервера — обязательно

Бэкап на том же диске не спасёт при отказе сервера, его блокировке или
шифровальщике. Нужна независимая копия.

**Вариант 1 — снапшоты провайдера (проще всего).** В панели включите
автоматические снапшоты диска. Стоит 10–20% от цены сервера.

**Вариант 2 — Yandex Object Storage.**

```bash
# Установка s3cmd:
sudo apt install -y s3cmd

# Настройка (нужны ключи сервисного аккаунта с ролью storage.editor):
s3cmd --configure
# Access Key / Secret Key — из сервисного аккаунта Yandex Cloud
# S3 Endpoint: storage.yandexcloud.net
# DNS-style template: %(bucket)s.storage.yandexcloud.net

# Ежедневная синхронизация в 04:30 (после создания бэкапа в 03:30):
crontab -e
```

```cron
30 4 * * * /usr/bin/s3cmd sync /var/backups/loaddevice/ s3://ваш-бакет/loaddevice/ >> /var/log/loaddevice-s3.log 2>&1
```

### 15.5. Проверьте восстановление

Бэкап, из которого ни разу не восстанавливались, — не бэкап.
**Проведите тестовое восстановление сейчас**, пока данных мало и ошибка
не критична. Порядок — в §20.

Повторяйте проверку раз в квартал.

## 16. Мониторинг и логи

### 16.1. Где смотреть логи

```bash
pm2 logs loaddevice --lines 100        # приложение
sudo tail -f /var/log/nginx/loaddevice-error.log    # ошибки nginx
sudo tail -f /var/log/nginx/loaddevice-access.log   # запросы
sudo journalctl -u postgresql -n 50    # PostgreSQL
sudo tail -50 /var/log/loaddevice-backup.log        # бэкапы
```

### 16.2. Ротация логов (обязательно)

Без ротации логи PM2 растут бесконечно и однажды заполнят диск —
после этого перестанет работать и приложение, и БД.

```bash
pm2 install pm2-logrotate
pm2 set pm2-logrotate:max_size 10M
pm2 set pm2-logrotate:retain 14           # хранить 14 файлов
pm2 set pm2-logrotate:compress true
pm2 set pm2-logrotate:rotateInterval '0 0 * * *'
```

Логи nginx ротирует сам (`/etc/logrotate.d/nginx`), настройка не требуется.

### 16.3. Мониторинг доступности (настоятельно рекомендуется)

Чтобы о падении сайта вы узнавали не от клиентов.

1. Зарегистрируйтесь на [uptimerobot.com](https://uptimerobot.com)
   (бесплатно до 50 проверок).
2. **Add New Monitor:**
   - Type: `HTTP(s)`
   - URL: `https://ВАШ_ДОМЕН.ru/api/health`
   - Interval: 5 минут
   - Alert contacts: ваш e-mail (можно добавить Telegram)

Эндпоинт `/api/health` возвращает `200` только если приложение
действительно работает **и** доступна база данных. При недоступной БД
он отдаёт `503`, поэтому вы узнаете о проблеме, даже когда сам процесс
Node ещё жив.

### 16.4. Мониторинг ошибок (желательно)

Логи показывают, что что-то упало, но искать в них причину неудобно.

## 18. Обновление проекта

### Рекомендуемый production workflow

1. Локально: `git push origin main`
2. На сервере: `bash /var/www/loaddevice/update-project.sh`  
   **или** GitHub Actions (после настройки секретов) — он вызывает тот же скрипт.

Авторизация пользователей: JWT в HttpOnly cookies (`access_token` 15 мин, `refresh_token` 7 дней). При смене `JWT_SECRET` / `JWT_REFRESH_SECRET` все сессии станут недействительны.

Вложения коммерческих предложений хранятся в `uploads/commercial/` — каталог должен попадать в бэкапы (`scripts/backup.sh` уже включает `uploads/`).

### ⚡ Быстрое обновление сайта одной командой

Со своей локальной машины:

```bash
ssh deploy@203.0.113.10 "bash /var/www/loaddevice/update-project.sh"
```

Это **основная и рекомендуемая команда** обновления production-сервера.

Скрипт `update-project.sh` выполняет по порядку:

1. находит node/npm/pm2 в PATH (работает и в неинтерактивной SSH-сессии);
2. проверяет наличие `.env`;
3. **делает бэкап БД** — до миграций, чтобы было куда откатиться;
4. `git fetch origin && git reset --hard origin/main`;
5. `npm ci` — установка строго по `package-lock.json`;
6. `npm run build`;
7. `npm run db:migrate` — версионные миграции;
8. `pm2 reload` с корректным завершением текущих запросов;
9. **проверяет `/api/health`** до 30 секунд;
10. **автоматически откатывается** на предыдущий коммит, если любой из
    шагов 5–9 провалился.

Благодаря шагам 9–10 неудачное обновление не оставит сайт лежащим:
при ошибке вернётся предыдущая рабочая версия, а в выводе будут логи
ошибок. Скрипт возвращает ненулевой код возврата при неудаче — это можно
использовать в автоматизации.

### 18.1. Порядок работы

Обновление всегда идёт через GitHub — правки прямо на сервере запрещены,
их сотрёт `git reset --hard` при следующем обновлении.

```
локальная машина → git push → GitHub → сервер (update-project.sh)
```

### 18.2. Шаг 1: отправьте изменения на GitHub

```powershell
# Windows PowerShell, в папке проекта:
.\update-github.ps1 -Message "описание изменений"
```

Либо вручную:

```bash
git add .
git commit -m "описание изменений"
git push origin main
```

**Убедитесь, что изменения действительно на GitHub** — сервер забирает
именно `origin/main`:

```bash
git rev-parse HEAD
git fetch origin && git rev-parse origin/main
# Должны совпасть
```

### 18.3. Шаг 2: обновите сервер

```bash
ssh deploy@203.0.113.10 "bash /var/www/loaddevice/update-project.sh"
```

### 18.4. Автоматический деплой (CI/CD)

В репозитории настроен GitHub Actions (`.github/workflows/deploy.yml`):
при пуше в `main` он сначала проверяет типы и сборку, и только затем
деплоит на сервер по SSH.

Чтобы включить, добавьте секреты в **Settings → Secrets and variables →
Actions**:

| Секрет | Значение |
|---|---|
| `SERVER_HOST` | IP сервера, например `203.0.113.10` |
| `SERVER_USER` | `deploy` |
| `SERVER_PORT` | `22` |
| `SSH_PRIVATE_KEY` | приватный ключ целиком, включая строки `-----BEGIN...` |

Создайте для CI отдельный ключ, не переиспользуйте личный:

```bash
ssh-keygen -t ed25519 -C "github-actions" -f ~/.ssh/gh_actions -N ""
cat ~/.ssh/gh_actions.pub >> ~/.ssh/authorized_keys
cat ~/.ssh/gh_actions        # это значение → в секрет SSH_PRIVATE_KEY
```

> Пока секреты не заданы, workflow будет падать на шаге деплоя. Это
> нормально: проверка сборки при этом всё равно работает и защищает
> `main` от нерабочего кода. Если автодеплой не нужен, обновляйте
> сервер командой из §18.3.

### 18.5. Если изменилась схема БД

Схема живёт в `shared/schema.ts`. После её правки **локально**
сгенерируйте миграцию и закоммитьте её:

```bash
npm run db:generate       # создаст SQL-файл в migrations/
git add migrations/ shared/schema.ts
git commit -m "db: описание изменения схемы"
git push origin main
```

На сервере миграция применится автоматически (`update-project.sh`, шаг 7).

> ⚠️ Не запускайте `npm run db:push` на сервере — см. предупреждение в §11.1.

### 18.6. Ручное обновление (если скрипт недоступен)

```bash

git fetch origin && git reset --hard origin/main
```

### 18.7. Откат к предыдущей версии

`update-project.sh` откатывается сам. Вручную:


## 19. Эксплуатация: типовые задачи

### 19.1. Продление домена

Домен продлевается в панели регистратора, а не на сервере.

1. Держите **автопродление включённым** и следите, чтобы на счету
   регистратора были деньги.
2. За 30 дней до истечения регистратор пришлёт письмо — не игнорируйте его.
3. Проверить дату окончания: `whois example.ru | grep -i "paid-till"`.

Если домен всё же истёк: он попадает в карантин на ~30 дней, сайт и почта
не работают. В этот период домен ещё можно выкупить у регистратора; после
карантина он уходит в свободную продажу.

### 19.2. Замена SSL-сертификата

Let's Encrypt продлевается автоматически (§13.3). Ручные сценарии:

```bash
# Принудительно продлить сейчас:
sudo certbot renew --force-renewal
sudo systemctl reload nginx

# Добавить домен к существующему сертификату:
sudo certbot --nginx -d example.ru -d www.example.ru -d new.example.ru

# Посмотреть сроки:
sudo certbot certificates
```

Если у вас **коммерческий сертификат** (не Let's Encrypt):

```bash
sudo mkdir -p /etc/ssl/loaddevice
sudo cp fullchain.crt /etc/ssl/loaddevice/
sudo cp private.key   /etc/ssl/loaddevice/
sudo chmod 600 /etc/ssl/loaddevice/private.key

sudo nano /etc/nginx/sites-available/loaddevice
#   ssl_certificate     /etc/ssl/loaddevice/fullchain.crt;
#   ssl_certificate_key /etc/ssl/loaddevice/private.key;

sudo nginx -t && sudo systemctl reload nginx
```

Проверка: `echo | openssl s_client -connect example.ru:443 2>/dev/null | openssl x509 -noout -dates`

### 19.3. Замена API-ключей и секретов

Общий порядок для любого ключа:

```bash
cd /var/www/loaddevice
cp .env .env.backup-$(date +%F)     # на случай ошибки
nano .env                            # впишите новое значение
chmod 600 .env
pm2 reload ecosystem.config.cjs --update-env    # ОБЯЗАТЕЛЬНО --update-env
pm2 logs loaddevice --lines 30       # убедитесь, что стартовало без ошибок
```

Особенности отдельных секретов:

| Секрет | Последствия замены |
|---|---|
| `YANDEX_POSTBOX_*` | Ничего не ломается. Старый ключ удалите в консоли Yandex Cloud |
| `JWT_SECRET` | **Все пользователи разлогинятся.** Меняйте в непиковые часы |
| `JWT_REFRESH_SECRET` | То же. Обязан отличаться от `JWT_SECRET` |
| `CSRF_SECRET` | Открытые страницы потребуют обновления (F5). Некритично |
| `DATABASE_URL` | Сначала смените пароль в самой БД (см. ниже), потом в `.env` |

Смена пароля пользователя БД:

```bash
sudo -u postgres psql -c "ALTER USER loaddevice_user WITH PASSWORD 'новый_пароль';"
# затем обновите DATABASE_URL в .env и перезапустите приложение
```

**Если секрет мог утечь** (попал в git, в скриншот, в переписку) — меняйте
немедленно и считайте все ранее выданные токены скомпрометированными.

### 19.4. Перенос проекта на другой сервер

```bash
# --- НА СТАРОМ СЕРВЕРЕ ---
cd /var/www/loaddevice
bash scripts/backup.sh
ls -t /var/backups/loaddevice/     # запомните имена свежих файлов

# Скачайте копии на локальную машину:
# scp deploy@СТАРЫЙ_IP:/var/backups/loaddevice/loaddevice-db-*.dump ./
# scp deploy@СТАРЫЙ_IP:/var/www/loaddevice/.env ./env-backup
```

```bash
# --- НА НОВОМ СЕРВЕРЕ ---
# Пройдите §5–§8 (пользователь, фаервол, Node, PostgreSQL, nginx, клонирование).

# Загрузите .env и дамп:
# scp ./env-backup deploy@НОВЫЙ_IP:/var/www/loaddevice/.env
# scp ./loaddevice-db-*.dump deploy@НОВЫЙ_IP:/tmp/

cd /var/www/loaddevice
chmod 600 .env

# Восстановите БД:
pg_restore --clean --if-exists --no-owner --no-privileges \
  --dbname="postgresql://loaddevice_user:ПАРОЛЬ@localhost:5432/loaddevice_db" \
  /tmp/loaddevice-db-*.dump

npm ci && npm run build && npm run db:migrate
pm2 start ecosystem.config.cjs && pm2 startup && pm2 save
```

Затем:

1. Настройте nginx (§12) и получите **новый** сертификат (§13) — старый
   привязан к старому серверу.
2. **Заранее** снизьте TTL DNS-записей до 300 секунд (за сутки до переноса) —
   так переключение пройдёт быстро.
3. Измените A-записи на IP нового сервера (§4.1).
4. Дождитесь распространения: `dig +short example.ru`.
5. Убедитесь, что новый сервер работает, и **только потом** выключайте старый.
6. Не удаляйте старый сервер минимум неделю — это ваш путь к откату.
7. Настройте бэкапы и мониторинг на новом сервере (§15, §16).

### 19.5. Перезагрузка сервера

```bash
sudo reboot
# через минуту:
pm2 status && curl -s http://127.0.0.1:5000/api/health
```

Если после перезагрузки приложение не поднялось — не выполнен `pm2 save`

## 20. Аварийное восстановление

### 20.1. Быстрая диагностика

```bash
pm2 status                                  # процесс жив?
pm2 logs loaddevice --err --lines 50        # что в ошибках
sudo systemctl status nginx postgresql      # сервисы живы?
df -h                                       # есть место на диске?
free -h                                     # есть память?
curl -s http://127.0.0.1:5000/api/health    # приложение отвечает?
```

Ответ `{"status":"degraded","db":{"status":"unavailable"}}` означает, что
приложение работает, а база недоступна: `sudo systemctl restart postgresql`.

### 20.2. Восстановление базы данных

Скрипт `scripts/restore.sh` делает это безопасно: перед восстановлением он
снимает страховочный дамп текущего состояния и требует подтверждения.

```bash
cd /var/www/loaddevice

bash scripts/restore.sh --list      # какие копии есть
bash scripts/restore.sh --db /var/backups/loaddevice/loaddevice-db-20260807-033000.dump
```

Скрипт остановит приложение, восстановит данные, применит миграции и
запустит приложение обратно. Введите `RESTORE` для подтверждения.

Восстановить самые свежие копии файлов и БД сразу:

```bash
bash scripts/restore.sh --latest
```

### 20.3. Восстановление файлов и `.env`

```bash
bash scripts/restore.sh --files /var/backups/loaddevice/loaddevice-files-20260807-033000.tar.gz
```

Текущий `.env` сохранится рядом с суффиксом `.before-restore-*`.

### 20.4. Полная потеря сервера

1. Возьмите новый сервер у провайдера.
2. Пройдите §5–§8 (базовая настройка и клонирование).
3. Восстановите `.env` и БД из внешней копии (§15.4) командами из §20.2–20.3.
4. Настройте nginx (§12), получите SSL (§13), поднимите PM2 (§14).
5. Переключите DNS на новый IP (§4.1).
6. Настройте бэкапы и мониторинг (§15, §16).

Ориентировочное время — 1–2 часа при наличии внешней резервной копии.
**Без внешней копии данные не восстановить** — вернитесь к §15.4.

### 20.5. Компрометация сервера

Признаки: неизвестные процессы, всплеск трафика, изменённые файлы,
незнакомые записи в `~/.ssh/authorized_keys`.

1. **Не удаляйте логи** — они нужны для разбора.
2. Ограничьте доступ: `sudo ufw default deny incoming`.
3. Смените **все** секреты: пароль БД, `JWT_SECRET`, `JWT_REFRESH_SECRET`,
   `CSRF_SECRET`, ключи Postbox, пароли администраторов, SSH-ключи (§19.3).
4. Проверьте `~/.ssh/authorized_keys`, `crontab -l`, `sudo crontab -l`,
   `last -20`, `ps aux` на посторонние записи.
5. Надёжный путь — развернуть чистый сервер (§20.4) и восстановить только
   данные из бэкапа, сделанного **до** взлома.
6. Если могли утечь персональные данные — по 152-ФЗ уведомление
   Роскомнадзора направляется в сжатые сроки (первичное — в течение 24
   часов с момента обнаружения). Уточните порядок у юриста.

## 21. Устранение неполадок

### Приложение не запускается

```bash
pm2 logs loaddevice --err --lines 50
```

| Сообщение в логах | Причина и решение |
|---|---|
| `🚨 Preflight: запуск невозможен` | Ошибка в `.env` — конкретные пункты перечислены ниже сообщения |
| `DATABASE_URL` не задан | Нет `.env` или нет строки `DATABASE_URL`. Проверьте: `ls -l .env` |
| `Ошибка подключения к базе данных` | `sudo systemctl status postgresql`; проверьте пароль в `DATABASE_URL` |
| `EADDRINUSE` | Порт 5000 занят: `sudo lsof -i :5000`, снимите лишний процесс |
| `JWT_SECRET NOT SET` | Добавьте секреты в `.env` (§9.1) |
| `JWT_REFRESH_SECRET must differ` | Секреты совпали — сгенерируйте разные значения |
| `Cannot find module '/var/www/loaddevice/dist/index.js'` | Не выполнена сборка: `npm run build` |
| `heap out of memory` при сборке | Не хватает RAM — настройте swap (§6.6) |

### 502 Bad Gateway

nginx работает, а приложение — нет.

```bash
pm2 status                                    # online?
curl http://127.0.0.1:5000/api/health         # отвечает?
sudo tail -20 /var/log/nginx/loaddevice-error.log
```

Если приложение отвечает на localhost, а nginx отдаёт 502 — проверьте,
что `proxy_pass` в конфиге указывает на правильный порт, и совпадает ли
он с `PORT` в `.env`.

### Сайт открывается по IP, но не по домену

DNS ещё не обновился или указывает не туда:

```bash
dig +short example.ru      # должен вернуть IP сервера
```

Также проверьте, что домен вписан в `server_name` конфига nginx.

### Не приходят письма

```bash
pm2 logs loaddevice | grep -i email
```

Проверьте по порядку:
1. `EMAIL_PROVIDER=yandex`, а не `noop`;
2. заданы `YANDEX_POSTBOX_KEY_ID` и `YANDEX_POSTBOX_SECRET`;
3. `MAIL_FROM_EMAIL` — в **подтверждённом** в Postbox домене;
4. в DNS добавлены SPF, DKIM, DMARC (§10.1);
5. письмо не в папке «Спам».

Тестовая отправка — в админке, раздел настроек почты.

### Cookie не сохраняются / постоянно разлогинивает

Почти всегда — `FORCE_SECURE_COOKIES=false` при работе по HTTPS.
Поставьте `true` и `pm2 reload ecosystem.config.cjs --update-env`.

### Всех пользователей блокирует после чужих неудачных входов

`TRUST_PROXY=false` при работе за nginx: приложение видит у всех
клиентов IP `127.0.0.1` и считает их одним человеком. Поставьте
`TRUST_PROXY=true` и перезапустите с `--update-env`.

### Диск заполнен

```bash
df -h
sudo du -h --max-depth=1 /var | sort -hr | head
pm2 flush                                        # очистить логи PM2
sudo journalctl --vacuum-time=7d                 # сжать системные логи
```

Если место съели бэкапы — уменьшите `KEEP_DAYS` в
`/etc/loaddevice-backup.env`. Если логи PM2 — настройте ротацию (§16.2).

### Ошибка миграций

```bash
npm run db:migrate       # прочитайте текст ошибки целиком
```

Не запускайте `db:push` «чтобы просто заработало» — он может обрезать
таблицы. Если миграция применилась частично, восстановите БД из бэкапа
(§20.2) и разберитесь с миграцией локально.
